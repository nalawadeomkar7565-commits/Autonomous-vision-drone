Multi-Rate Control System Analysis

Vision FPS vs. Flight Controller Frequency & ML Model Sizing

1. System Frequency Discrepancy

In a typical autonomous drone architecture, the companion computer (vision system) and the flight controller operate at different frequencies. For instance, an optimized vision pipeline might output target coordinates at 85 FPS, while the flight controller's position estimation/MAVLink intake loop processes inputs at 30 to 50 Hz.

Consequently, 35 to 55 vision updates per second are technically skipped or overwritten. Flight controller firmware (e.g., ArduPilot, PX4) reads incoming serial messages on a fixed scheduler. If 85 messages are pushed into the serial buffer in one second, the flight controller's Extended Kalman Filter (EKF) will simply grab the most recent message available when its 30Hz or 50Hz timer triggers, discarding older unread messages.

Mechanical Inertia Limits

The control rate bottleneck naturally shifts to the flight controller's navigation loop. This is a desirable limitation. A physical drone (frame, ESCs, motors, propellers) cannot dynamically react to changes in direction faster than 30 to 50 times a second. Updating position commands faster than 50 Hz yields diminishing returns due to physical inertia.

Multi-Loop Architecture

Flight controllers utilize a cascaded loop structure:

Inner Loop (Rate/Gyro): Runs at 1,000–8,000 Hz, updating motor speeds for stabilization.
Outer Loop (Navigation): Runs at 30–100 Hz. The companion computer injects vision data here, dictating desired trajectory, which is passed to the inner loop.

2. Advantages of an Over-Frequency Vision Pipeline

Even though intermediate frames are dropped, maintaining a vision processing pipeline significantly faster than the flight controller's polling rate (e.g., 85 FPS vs 50 Hz) provides critical functional advantages.

Advantage A: Maximum Data Freshness

When the FC reaches into the buffer at a 50 Hz interval (every 20ms):

  • At 30 FPS vision, the newest frame may be up to 33ms old.
  • At 85 FPS vision, the newest frame is a maximum of 11.7ms old.

This ensures the FC receives the freshest data possible, minimizing phase lag and preventing trajectory overshoot during high-speed tracking.

Advantage B: Temporal Filtering

Generating data at 85 FPS provides the companion computer with excess data points. This allows for lightweight temporal filtering (such as a Kalman Filter or Moving Average) directly on the bounding box coordinates before transmission. Anomalous frames resulting from motion blur or momentary false detections can be mathematically smoothed out prior to FC intake.

3. Buffer Margins and System Jitter

To guarantee reliable drone performance, control systems engineering dictates that the sensor update rate (Vision FPS) should ideally be 1.5x to 2.0x the frequency of the flight controller's navigation loop.

  • FC at 30 Hz: Target vision output of 45 to 60 FPS.
  • FC at 50 Hz: Target vision output of 75 to 100 FPS.

Overcoming Operating System Jitter

A standard Linux OS is not a strict real-time system. Frame processing times will fluctuate (jitter). A 1.5x buffer ensures that if a single frame takes longer than average due to background CPU tasks, the flight controller is never starved of new data.

The Danger of a 1:1 Ratio

The absolute minimum acceptable ratio is 1:1. However, this offers zero buffer margin. If a single frame is dropped or delayed, the flight controller will poll an empty buffer and reuse stale coordinate data, resulting in physical micro-stuttering during flight. A safe, practical minimum is to maintain at least +15 FPS above the FC frequency. For example, a 70 FPS vision system feeding a 50 Hz FC yields a 1.4x ratio, which is a highly reliable boundary.

4. YOLOv8 Model Sizing Constraints

Attempting to match the vision system's FPS perfectly to the flight controller's frequency by deliberately selecting a heavier, slower Machine Learning model destroys the necessary safety buffer. The YOLOv8 architecture scales significantly, and moving to heavier models drastically increases the computational load beyond the capabilities of edge hardware.

YOLOv8m Medium 25.9 M 78.9 GFLOPs Entry-level desktop GPUs, high-end robotics platforms (e.g., Jetson Orin).

Note: Moving from the Small (s) to the Medium (m) model more than doubles the parameters and nearly triples the mathematical load. Running YOLOv8m on an edge configuration would cause frame rates to crash below standard FC 50 Hz thresholds, breaking the control loop.
